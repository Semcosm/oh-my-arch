## Summary

Add a tag-driven GitHub Release workflow and prepare the project version and release notes for `v0.0.1`.

## Motivation

The project now has a verified remote build path, so the next milestone is publishing predictable ISO artifacts without storing generated files in the repository.

## Test Evidence

The existing remote `oma-build` and `oma-check` workflows pass. The new release workflow reuses the same Arch Linux container build, checksum verification, pinned checkout action, and repository release metadata. Local policy, quality, supply-chain, action-pinning, and repository-shape checks will run before integration.

## Risk

The release path depends on GitHub tag events, the hosted runner, Docker, and the GitHub CLI. A failed release run does not modify the repository contents and can be retried from the tag.

## Rollback

Remove the release workflow and release notes, restore the default project version, and delete the unneeded release tag or GitHub Release.

## Breaking Change

No CLI or profile behavior changes. The default project version changes from `0.1.0` to `0.0.1` for the first public release.

## Backport Target

None.
